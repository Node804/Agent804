# Agent804 0.5 field trials

Status: historical 0.5 proposed protocol, superseded for 0.6; no trials executed by writing
this plan. Its unconditional completion-hook probes are not current setup instructions.
All supplied Stop adapters are withdrawn in 0.6. Use direct checks/CI and the release
preparation plan in `0.6.0-release.md`; GR-8 requires separate opt-in and supported integration.

## Purpose and order

Test whether the current kit is usable, enforced and useful on real work. Run trials 1–4
on one reference project and one host first. Trial 5 checks transfer after defects are fixed.
Use an existing application with real pending work; synthetic probes test controls only.
Keep project identities in private project records; publish only anonymized evidence here.

| Trial | Question | Suggested session budget |
|---|---|---|
| 1. Setup and enforcement | Can the installed kit guide setup and block incomplete work? | 60–90 minutes |
| 2. Small bug | Is the small-change path usable without coaching? | 45–90 minutes |
| 3. Feature and recovery | Can the full flow survive independent handoffs and interruption? | 2–4 hours |
| 4. Correction and maintenance | Does feedback become an exercised prevention? | 60–90 minutes, then revisit |
| 5. Transfer | Can another developer or host repeat the workflow? | 2–3 hours |

Budgets are planning estimates, not performance standards. Before each run, the developer
sets an acceptable human-time budget. At the limit, record the state and decide whether to
continue; an unfinished run stays incomplete. Spread the work across ordinary sessions.

## Common protocol

- Pin the kit revision plus any uncommitted patch; pin the application's starting revision.
  Preserve patches for dirty work. Record installed resources, host/client version, model,
  effort, OS/shell, tools, available CI and developer familiarity. Unknown stays unknown.
- Use normal isolated development resources and synthetic data. Keep deliberate violations
  in a disposable checkout. Publishing, commits and external writes retain existing consent.
  This plan authorizes no installation, host launch or paid evaluation by itself.
- Freeze the kit during a run. If instructions need repair, record the failure, retain the
  original evidence, change the kit separately and repeat from the same starting artifacts.
- Give the agent the task, kit and project records. Do not coach it through hidden steps.
  Answer legitimate product questions; record procedural rescue separately from clarification.
- Use sequential fresh sessions for tests, implementation and review. Test writers receive
  agreed criteria and existing contracts/code, without the new implementation. Reviewers see
  criteria and diff, without the implementer's conclusions. Record actual input boundaries.
- Record actual commands, exit codes, test counts/skips and output artifacts. Preserve initial
  failures and review findings. A retry or later repair does not erase the first outcome.
- Use Pass, Fail, Incomplete or Unavailable for each assertion. Pass needs observed evidence;
  Unavailable blocks the relevant claim. Record assisted completion separately from an
  unassisted pass. Make no overall effectiveness claim from one successful task.

## Trial 1: setup and actual-host enforcement

Choose an existing application with a useful but incomplete harness. Record existing failures
and mechanisms first. Use the intact kit's current `adopt` skill for one bounded increment.

Starter prompt:
> Use Agent804 adopt on this repository. Establish or connect one check command using the
> existing tools, preserve application behavior, and record remaining gaps. Prove the
> configured completion control in this host. Ask me about project-specific choices.

Observe these probes in a disposable checkout after setup:
1. A known-good check runs and succeeds; test discovery matches the expected suite.
2. A deliberate failing assertion produces a nonzero check and visible failure evidence.
3. Exercise the host's normal completion path with that failure present. Verify the actual
   hook invokes the check and blocks successful completion or continues for correction.
   An agent voluntarily reporting failure without a hook event proves reporting only.
4. Restore the passing case and observe successful completion. Then modify a checked file
   to fail again: an old green result must not authorize completion of the changed tree.
5. Trigger a harmless hook execution error, such as a nonexistent fixture command; record
   actual host behavior. The error must not be recorded as a passing check. Document any
   bounded failure-report escape separately from successful completion.

Pass: the increment preserves existing behavior; all applicable probes have direct evidence;
the project host record distinguishes configured controls from exercised controls. No broad
formatter migration, unrelated repair or invented clean baseline is needed to finish setup.
If the host cannot enforce completion, record that capability as unavailable or failed and
keep it explicit in later trials; useful workflow observations can still continue.

## Trial 2: the small-change path

Pick a real, localized bug with an observable reproduction, no red-zone change and no
architecture decision. Example shape: one filter incorrectly includes an excluded record.
Before starting, write the expected result privately so the evaluation is not retrofitted.

Starter prompt:
> Use Agent804 to fix this bug: <observable reproduction and expected result>. Keep the
> change local and use the small-change path. Show the verification and final diff.

Run the current `spec` → independent tests → implementation → independent `review` flow.
The developer agrees criteria and reviews the final change. Let the skill choose its files;
record unnecessary documents, repeated explanations, questions and session-transfer effort.

Pass: the intended regression is shown before the fix; unrelated test checks work; acceptance
tests remain unchanged during implementation; the full check passes; human review confirms
the behavior and scope; no procedural rescue was necessary. Record time-budget satisfaction
separately: a correct but cumbersome run is evidence to simplify the small-change workflow.
Recheck for regression during the next work session and record the actual observation window.

## Trial 3: medium feature, design and interrupted recovery

Pick a real feature across at least two boundaries, with an authorized path, a refusal or
invalid-input path, and existing behavior to preserve. Avoid live external writes. Example
shape: archive an item through the UI and API while retaining read access to its history.
Use existing ADRs; exercise `decide` only if a real hard-to-reverse choice arises.

Starter prompt:
> Use Agent804 for <feature and user outcome>. Apply the project's current contracts and
> decisions. Agree the criteria, plan the work, and use independent tests and review.

First observe the current kit without adding instructions about program design or slices.
Record whether the plan makes interfaces, call paths and demonstrable increments reviewable,
or leaves them implicit until the implementation. This is a diagnostic, not an existing gate.

After independent tests are written and run, end the session at a recorded boundary. In a
fresh implementation session, provide the repository and durable handoff only, without a
verbal recap. Preserve uncommitted work through an exact patch when a different checkout is
used. Ask the new session to identify scope, relevant contracts, verification state and next
action before making changes. Compare that account with the operator's recorded state.

Pass: all agreed paths and preservation cases are verified; initial test failures are
behaviorally relevant; handoffs preserve independent inputs; recovery identifies the exact
state without inventing results or requesting already recoverable consent; independent
review and human review are completed with findings resolved or explicitly outstanding.
The feature cannot be called complete while an agreed criterion remains unmet.

If code-shape review or slicing was missing, propose a minimal kit change after this run.
Test that change on another comparable feature, with similar host/model/effort and scope.
Record review effort and rework; task and learning differences prevent a causal speed claim.

## Trial 4: correction → sensor → maintenance → measurement

Use a real recurring correction from trials 2–3 or the project's intervention history.
Choose an invariant suitable for automation. Do not manufacture recurrence to justify a
check. If no suitable correction exists, defer this part and report the missing evidence.

Starter prompt:
> Use Agent804 sensor for this repeated correction: <examples and expected invariant>.
> Prove the check detects it and include it in our existing check command.

Observe the current code, an isolated reintroduced violation that fails, and its correction
that passes. A valid contrasting case must also pass. Record false positives, exemptions and
any required policy review. An ordinary later change should exercise the check again; its
absence of a violation alone does not prove the agent learned the rule.

Then run `garden` on the affected scope: confirm or reject drift candidates, record a reviewed
repair or explicit disposition, and verify any repair against the code. No invented drift
is required. Run `measure` using the captured interventions, checks, review time and rework.
If no prior period exists, report this period as the baseline with no improvement percentage.

Pass: the prevention demonstrably detects the invariant violation without rejecting the valid
case, runs through the project's check, and the correction links to that evidence. Gardening
has grounded dispositions, and measurement preserves missing data. Mark the later recurrence
observation pending until a real follow-up change occurs; do not infer sustained improvement.

## Trial 5: transfer after repairing observed defects

Have someone other than the author run a fresh small task with the installed kit and the
developer guide, without live coaching. Prefer a second reference project. Record which
conditions changed; success establishes only that combination, not general portability.

Separately, repeat trial 1's control probes and a small bug on a second host using the same
starting fixture/task artifacts and equivalent permitted inputs. Keep host results separate
from real-project results. Fix known defects before testing the repaired kit and retain both
versions' results. A host comparison is not a model ranking.

Pass: the new operator completes the workflow without procedural rescue; resources resolve;
the second host's capabilities have their own observed evidence. Report task completion and
enforcement independently when one succeeds and the other does not.

## Evidence record for every run

Keep raw outputs and identities in the reference project's existing records. Publish a short
anonymized summary here only after reviewing it for private information.

| Field | Record |
|---|---|
| Run and conditions | Trial/date, kit/app revisions or patches, host/model/effort and resources |
| Task and expected outcome | Criteria, invariant/probe, starting failures and allowed scope |
| Session boundaries | Actual inputs and exact handoff artifacts for each role |
| Human time | Active setup, clarification, handoff, review and correction minutes separately |
| Elapsed time | Start/end; distinguish tool waits and interruptions from active time |
| Correctness | Criteria exercised, defects, final check command/status/counts and limits |
| Friction | Procedural rescues, repeated questions, unnecessary artifacts, unrelated edits |
| Rework | What changed after review and why; preserve original findings |
| Later observation | Next-change result, regressions/recurrence, date and observation limits |
| Outcome | Per-assertion status, assisted/unassisted completion, artifacts and next action |

Compare time and outcomes descriptively. A historical task is usable as a baseline only when
its scope and actual time evidence are comparable; do not reconstruct missing timings.

## Decisions after the first four trials

Fix demonstrated workflow failures before expanding the trial matrix. Promote evidence only
for the exact skill text, task, stack and host exercised. One run supports “used once”; retain
fixture-only, untested and failed parts explicitly. Update README evidence and validation
records from reviewed results, never from this protocol. Further trials for `start`, Operate,
Security, parallel resources and cumulative assessment remain separate work.
