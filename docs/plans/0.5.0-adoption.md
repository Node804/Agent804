## Isolated forward exercise

An independent evaluator used `adopt` in a disposable existing Python 3.12 repository with
one function, one unittest and a README test command. It had its own unborn task branch;
no dependencies or live services were needed. The evaluator was given developer requests
and raw files, not an expected implementation.

First request: create concise instructions, a check wrapping existing tests and a resume
record; no dependency installation or behavior changes. The skill produced `AGENTS.md`,
`scripts/check.py`, an adoption record, a scoped Draft mechanisms note and execution evidence.
Baseline/repeated unittest runs passed one test with exit 0. The partial check reported
one discovered/executed test, no skips and missing controls, and exited 1 honestly.

Negative probes in isolated copies exercised empty discovery (exit 1), assertion failure
(exit 1), skip name/reason/count reporting (exit 0), and instruction-budget breach (exit 1).
The copies removed only the declared missing-check list so failure propagation could be
distinguished from the actual runner's persistent incomplete-adoption result. Probe files
were removed. No test was weakened in the original project or kit.

Second request: continue by documenting Python style only, retaining deliberate conventions
and using the language standard where needed; no tool installs/configuration or formatting.
It reused the record, wrote concrete conventions in the existing Draft profile, linked
that authority and recorded future enforcement choices. Hashes confirmed the application,
test, README and runner bytes were unchanged. ST-1 remained partial; no level was invented.

The evaluator observed the original full-profile expansion before correction, then trimmed
the profile to the two increments. No other behavioral issue was reported. Both bounded
increments completed while adoption remained incomplete. Retained-versus-disposable use
was left as a destination question, without blocking the authorized setup.

This exercise does not verify a real formatter migration, CI, actual-host loading/hooks,
review enforcement, legacy-failure remediation or reduced developer overload. A developer
trial on a real codebase remains pending.

## Follow-up terminology review

Verified all five developer-supplied review findings against the current source. Acceptance
criteria for these focused wording fixes:

- The README explicitly requires both the claimed level's gates and every earlier gate.
- With no feature since adoption, TS-1 to TS-4, TS-8 and TS-9 remain not verifiable rather
  than failing on older code. They can support only a provisional level.
- A Level 2 prototype with TS-1, TS-6 or DC-1 to DC-3 outstanding receives a bounded action
  on those additions, not an obligation to implement the rest of Level 3. Urgent risks
  remain first; level progression is limited to the stated target.
- A proposed next increment remains unauthorized until the developer agrees its scope
  and completion evidence. A continuation record cannot itself supply consent.
- Operate marks `O1✓ O2✗` yield O1; `O1◐ O2✓` yield no level; `O1✓ O2✓*` yield O2.

All five source passages now state these outcomes explicitly. No gate memberships, rule
properties or module triggers changed. These are documentation/scoring-prose checks, not
new runtime behavior; no wording-matching unit tests were added.
