# 0.5.0: guided adoption and developer journeys

Status: Built; independent review and isolated forward exercise passed. Field trials pending.

The developer requested guidance for new projects, existing code and daily work, then
specified that `adopt` must walk through creating missing pieces, such as style guidance
or a check command, as `start` does for new projects. Adoption happens over time.

## Acceptance criteria

1. `adopt` works on existing code, preserves useful conventions and tools, and helps choose,
   create and exercise missing protections. It does not stop at a list of recommendations.
2. It asks only unanswered questions needed for the next step, one at a time with a default;
   agrees one bounded increment and its completion evidence before implementing it.
3. Missing style guidance leads to a project-owned convention, formatter/linter choices,
   non-mutating enforcement and a separate fix command; existing legacy findings do not
   trigger an unsolicited repository-wide reformat or weakened enforcement.
4. A missing check command leads to a real stack-appropriate runner combining available
   checks, propagating failure, reporting test counts and unexpected empty discovery, and
   documenting its actual scope. Missing tooling/tests remain gaps under their own rules;
   a partial runner never establishes Level 1 or a false full-check green result. CK-1
   retains its separate runner/CI contract rather than double-counting missing tools.
5. Adoption is resumable from a small repository record linking implemented evidence and
   the next increment. It does not require full assessment or finishing a level to begin.
6. `assess` stays read-only. Its report offers one bounded next action and at most two
   optional follow-ups, with urgent risks explicit and detailed findings retained.
7. A developer guide covers starting a project, gradual adoption and daily feature/bug/
   refactor work, with human responsibilities, sample requests and a practical example.
8. No new rule, level gate or module trigger is introduced; scores and existing failures
   remain honest. No commit, push or live host-policy change is implicitly authorized.
9. Kit checks and skill validation pass. Independent scenario review/forward testing checks
   actual adoption behavior; fixture evidence is distinguished from real-project trials.

This extends the 0.5 level spec's report recommendations: one next action replaces a
mandatory list of three tasks. No external reference is added or empirical claim inferred.
